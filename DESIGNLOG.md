# Design log

This log records consequential implementation decisions, their evidence, and the tradeoffs that future scanner work must preserve.

## 2026-08-04 — Require execution closure on self-hosted pull-request runners

**Decision.** Emit a same-file GitHub Actions CWE-284/CWE-829 hypothesis only when a pull-request-capable event schedules a job on a statically classifiable self-hosted or custom runner, the job checks out attacker-controlled pull-request bytes through the official Checkout action, and a later command or repository-local action executes from the affected workspace. Preserve the exact event, runner selection, checkout, execution sink, effective permissions, structural secret use, and candidate controls in one typed record.

**Why.** GitHub's secure-use guidance distinguishes ephemeral clean GitHub-hosted virtual machines from self-hosted runners, warns that untrusted workflow code can persistently compromise a self-hosted runner, and advises against using self-hosted runners for public repositories. CodeQL's experimental `actions/pr-on-self-hosted-runner` query assigns severity 9.0, high precision, and CWE-284, and CodeQL 2.26.0 updated its standard hosted-runner label classification to reduce false positives. Scheduling alone, however, does not prove that pull-request bytes execute. This implementation adds the missing Checkout-to-workspace-to-execution closure and preserves CWE-829 for the untrusted code-loading boundary.

**Runner and trigger boundary.** Recognize the literal `self-hosted` label even when another label is dynamic, static runner groups, and static custom labels. Exclude CodeQL 2.26.0's current GitHub-hosted Ubuntu, macOS, and Windows label forms and its BuildJet/Warp hosted forms; reject fully dynamic selection because the repository does not prove ownership. Recognize `pull_request`, `pull_request_target`, `issue_comment`, pull-request review and review-comment events, plus an explicitly closed `workflow_run` case. `workflow_run` does not inherit an inferred upstream checkout: it must independently contain an exact recognized pull-request checkout and later execution.

**Checkout, state, and impact boundary.** Under `pull_request`, official Checkout defaults and exact `github.sha`, `github.ref`, or pull-request merge SHA select untrusted merge-ref content. Explicit head SHA and fork repository forms remain recognized for the other supported events, including `github.event.number`, `github.event.issue.number`, and literal pull refs. An explicit fixed repository is trusted unless it is the current repository or an exact fork context. Workspace state follows checkout paths and workflow/job working directories; a clean trusted checkout clears overlapping taint, while `clean: false` does not. Checkout v7's default fork refusal is relevant to explicit privileged fork checkout, not ordinary `pull_request` merge-ref checkout. Ordinary `pull_request` rows never invent secret or write-token impact. Other event rows add those categories only from exact effective permission and structural secret evidence.

**Validation boundary.** Static custom labels and runner groups are candidates, not proof of customer ownership. Review must confirm the job resolves to a customer-controlled runner and examine persistence across later jobs, reusable work directories, service-account authority, signing keys, cloud metadata, internal network services, Docker sockets, tool caches, and release/deployment workloads. Immutable commit selection, read-only current-job permissions, disabled Checkout credential persistence, review labels, and environments constrain current impact but do not erase host compromise. A GitHub-hosted runner or a proven freshly provisioned, single-job JIT runner destroyed after the job is strong persistence counterevidence.

**Executable and regression evidence.** The paired workflows are identical except that the positive uses `[self-hosted, linux, x64]` and the control uses `ubuntu-latest`. The witness models a reusable runner where an untrusted pull-request job overwrites a user-writable release helper and a later privileged job observes a mock token; its hosted control destroys the pull-request machine and starts the later job from a trusted helper on a fresh machine. Thirteen focused tests cover the manifest, exact provenance, explicit/custom/group runners, current standard hosted exclusions, dynamic selection, default and explicit pull refs, event coupling, fixed repository rejection, workspace cleanup, Checkout v7 semantics, privilege categories, controls, strict YAML failure cases, deduplication, and reviewer guidance.

**Acceptance evidence.** The focused lane passes 13 tests and 72 assertions; the six adjacent GitHub Actions lanes pass 64 tests and 356 assertions. All six executable witnesses pass. The complete authoritative Windows suite passes 793 tests and 6,647 assertions across 106 files with 19 intentional environment-specific skips and no failures. Deterministic review emits one exact positive record at `.github/workflows/test.yml:12`, no hosted-control record, and no production-repository record. Formatting, generated-model drift, TypeScript checking, the production build, and the production advisory query are clean. The 207-entry archive passes strict inspection, two isolated installations, public import, CLI, and all 79 bundled-plugin file checks. The external fresh-key self-scan is deliberately not counted: sending the uncommitted repository and 128 reachable commits to Copilot was blocked pending separate explicit disclosure approval.

**Consequence.** The scanner now distinguishes a complete persistent-runner compromise opportunity from mere self-hosted scheduling and from clean hosted execution. Remaining work includes cross-file `workflow_run` provenance, organization runner-group policy resolution, GitHub larger-runner metadata, autoscaler/JIT lifecycle evidence, service-container and Docker-socket reachability, runner-controller configuration, and attack paths from one compromised job into specific later release jobs. Those extensions must preserve exact runner identity, lifecycle, workspace state, and execution closure rather than broadening every custom label into a confirmed vulnerability.

## 2026-08-04 — Bind workflow event fields to generated script source

**Decision.** Emit a same-file GitHub Actions CWE-094/CWE-095/CWE-116 hypothesis only when an exact supported workflow trigger makes an exact event context attacker-controlled and that value reaches a workflow `run` script or a code-interpreting input of one exact known action. Preserve the trigger, source context, optional workflow-expression environment alias, interpreter and input identity, effective permission, structurally available secret, and candidate controls in one typed record.

**Why.** GitHub documents that expressions embedded in inline scripts are substituted before the shell or action interpreter receives the generated program, so source-language quoting does not make attacker text data. Its preferred construction places the expression in an intermediate environment value and reads that value through the interpreter's native environment API. CodeQL rates Actions code injection security severity 9 with very-high precision and CWE-094/CWE-095/CWE-116. The cross-file reusable-workflow and composite-action models did not cover the common direct `${{ github.event.* }}` case. Conversely, a suffix match on event properties or every action `with` value would invent attacker capability and executable sinks. The model therefore couples supported events to exact fields and takes the current action code-input identities from CodeQL and zizmor rather than broadening ubiquitous YAML keys.

**Expression, scope, and sink boundary.** Parse only exact `.github/workflows/*.yml` or `.yaml` paths as strict YAML 1.2 with unique keys and no aliases. The bounded expression evaluator recognizes direct dot or single-quoted bracket contexts, enclosing parentheses, value-preserving `toJSON`, `fromJSON`, `format`, and `join`, and only reachable value-carrying `&&` or `||` arms. It deliberately rejects comparisons, `contains`, prefix/suffix predicates, unknown functions, fixed results, and unreachable short-circuit arms. Compute workflow, job, and step environment shadowing in order: an attacker-derived environment expression is a propagator only if the script later recompiles `${{ env.NAME }}`; a fixed override clears it, and native shell variables or `process.env` remain data. `run` is an interpreter sink. Action inputs are sinks only for one of 18 exact repository identities and its recorded code-bearing input under a literal revision; ordinary action data, unknown inputs, lookalikes, and expression-built revisions are not sinks.

**Privilege and control boundary.** Keep code execution distinct from ambient authority. `pull_request` makes the modeled fields attacker-controlled, but fork runs normally have read-only tokens and no ordinary secrets, so those impact categories are never inferred for that trigger. For default-branch-capable events, write-token impact requires effective write permissions and secret impact requires an inherited exact secret environment value or structural same-step `secrets.*`/`github.token` access. Workflow/job permission overrides, environment shadowing, read-only tokens, label review gates, and deployment environments remain explicit reviewer evidence. None of them silently sanitizes program text, and comments cannot create secret evidence.

**Executable and regression evidence.** The paired workflows receive `pull_request_target`, grant contents/OIDC write capability, and use official GitHub Script with a mock release-token environment. The positive inserts the pull-request title directly into JavaScript source; substitution of the harmless payload creates a second statement that observes the mock token. The control maps the same title into `TITLE` and reads only `process.env.TITLE`, producing one inert logged string. Eleven focused tests cover perfect manifest gates, exact source/sink/impact provenance, ordinary `pull_request` impact reduction, event/field coupling, dot and bracket contexts, bounded functions and short-circuit reachability, boolean-only rejection, all environment scopes and overrides, native use, `run`, all 18 action identities, unknown inputs and lookalikes, effective permissions, secret shadowing, review/environment leads, malformed/duplicate/aliased YAML, non-workflow paths, and reviewer guidance.

**Acceptance evidence.** The focused lane passes 11 tests and 95 assertions; the five adjacent GitHub Actions lanes pass 51 tests and 284 assertions. All five executable witnesses pass. The complete authoritative suite passes 780 tests and 6,575 assertions across 105 files with 19 intentional environment-specific skips and no failures. A managed-sandbox run initially denied the Windows ACL hardening used by temporary scanner homes and caused a synchronized child-process cascade; both representative cases and the complete suite passed at the intended host filesystem boundary without a product change. Deterministic fixture review emits exactly the vulnerable same-workflow expression-compilation path while the native-environment control and production source emit none. A fresh-key 128-commit self-scan examines 1,126 current plaintext files and 2,440 reachable historical plaintext blobs totaling 56,269,962 bytes with zero candidates, complete history, and no truncation. Formatting, generated-model drift, TypeScript checking, the production build, and the production advisory query are clean. The 207-entry archive passes strict inspection, two isolated installations, public import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** Review now receives a trigger-capable event source joined to the actual generated-program boundary instead of a raw expression warning, while GitHub's documented intermediate-environment defense remains a true negative. Additional event payloads, dynamic object indexing, `GITHUB_ENV` propagation, matrices, job outputs, shell-specific escaping, JavaScript-action internals, repository-owned custom actions, remote action versions, and self-hosted runner persistence remain future typed extensions. They should add explicit source capability, value semantics, and interpreter identity rather than weakening the exact event and sink maps.

## 2026-08-04 — Resolve workflow inputs into local composite-action interpreters

**Decision.** Emit a cross-file GitHub Actions CWE-094/CWE-095/CWE-116 hypothesis only when an exact externally influenced default-branch event controls one exact workflow-step input, that step invokes a literal repository-local action directory, exactly one `action.yml` or `action.yaml` in that directory declares the same input and selects `runs.using: composite`, and a runnable composite step interpolates the input or a same-step input-derived workflow-expression environment alias into `run` or official `actions/github-script` source. Preserve trigger, caller field, local action call, descriptor and input identity, optional environment alias, and interpreter sink as one ordered record.

**Why.** GitHub documents that Actions expressions are evaluated and substituted before a generated shell program runs, so quotes around attacker-controlled expression text do not establish a data boundary. Its composite-action tutorial demonstrates the safe construction: assign `${{ inputs.who-to-greet }}` to a step environment entry and read `$INPUT_WHO_TO_GREET` natively. GitHub's metadata reference separately states that composite actions do not receive automatic `INPUT_*` variables, require an `action.yml` or `action.yaml`, declare inputs in metadata, select `using: composite`, and require a shell for `run`. **Identity, flow, and control boundary.** Parse caller workflows and action metadata as strict YAML 1.2 with unique keys and no aliases. Couple each supported event to its exact attacker-controlled fields and accept only a direct caller expression. Normalize literal `./` action directories without resolving absolute, backslash, parent-traversing, or expression-built targets. Reject missing descriptors and the ambiguous case where both metadata names exist. Require action name and description, a declared same-name input with a description, the composite runtime, and a steps sequence. Direct input interpolation and same-step input-derived `${{ env.NAME }}` re-expansion close the code sink; native shell variables and `process.env` do not, and step-local environment taint does not leak into later steps. Require a scalar shell for composite `run`; accept only official semantic-version or full-commit-pinned GitHub Script identity and its `script` field. Preserve effective read-only caller permissions, job and step review labels, and deployment environments as leads. Classify secret exposure only when the caller explicitly forwards a `secrets.*` or `github.token` value under an input name that the exact sink step structurally consumes; YAML comments cannot create that category.

## 2026-08-03 — Require privileged trigger, untrusted checkout, and matched execution closure

Preserve trigger, untrusted ref, optional fork repository, checkout version and options, ordered workspace state, execution sink, and effective workflow/job privileges as separate evidence.

**Why.** GitHub documents `pull_request_target` as a privileged base-branch context and warns against executing untrusted code there, but the trigger intentionally checks out trusted base code by default. CodeQL's high-precision query requires the full privileged-trigger, attacker-controlled fork, checkout, and execution chain. OpenSSF Scorecard's trigger-plus-explicit-checkout rule is useful broad screening, but cannot by itself distinguish an unused checkout, an unrelated subpath, a trusted replacement, or current Checkout v7's default refusal of fork pull-request checkout. Requiring ordered path closure supplies the missing exploit boundary without treating every privileged maintenance workflow as vulnerable.

**Parser, flow, and control boundary.** Parse strict YAML 1.2 with unique keys and exact source ranges; reject malformed documents, aliases, and non-workflow paths rather than guessing. Accept only the official `actions/checkout` identity at a semantic version or full commit pin and an explicit pull-request head SHA/ref, pull-request ref, or pull-request head repository, including its default branch. Track taint per normalized checkout path inside each job, honor workflow/job/step working-directory precedence, replace duplicate workspace state, clear nested taint when a later trusted checkout replaces it, and emit only when a later package, build, test, interpreter, executable-script, or local-action step overlaps it. Inline interpreter/version commands, trusted absolute scripts, and package installation with lifecycle scripts disabled are not execution sinks. Retain Checkout v7 fork protection only when the semantic version is known and the workflow does not explicitly enable unsafe pull-request checkout; a commit pin remains version-unknown evidence for review. Retain immutable SHA, read-only effective permissions, disabled credential persistence, review labels, and deployment environments as independent control leads; retain secrets, OIDC, write permissions, and privileged workflow context as impact leads. No one lead alone proves or disproves exploitability, and label/environment approval remains subject to immutable-SHA and time-of-check/time-of-use review.

## 2026-08-03 — Bind Spring mass assignment to the persisted domain object

**Decision.** Emit a bounded Spring CWE-915 hypothesis only when an official `@ModelAttribute` parameter on an official state-changing MVC controller has the same simple domain type as the object passed to an official typed Spring Data `CrudRepository` or `JpaRepository` `save`. Require that type to resolve to exactly one official Jakarta or legacy Javax JPA entity inside the same Maven project. Preserve the same object directly, through one uniquely resolved service, or through exactly two uniquely resolved service boundaries.

**Why.** Spring MVC documents that `@ModelAttribute` uses constructor and property binding by default, explicitly warns that model binding can expose security-sensitive properties, and advises dedicated web-binding objects or allowed-field configuration. Spring Data documents `save` as persisting the supplied entity. A generic annotation-plus-method-name signal would be noisy: DTO projection, fixed entity construction, unrelated save arguments, GET handlers, local lookalikes, and mismatched repository domains are common counterexamples. Exact parameter, domain, receiver, and argument identity captures the dangerous boundary without treating ordinary form handling as a vulnerability.

**Type, flow, and control boundary.** The controller stereotype, mapping, model annotation, binder annotation and type, repository base, and entity annotation must be official imports, wildcards, or fully qualified names without a conflicting local declaration. Only POST, PUT, PATCH, or an equivalent official `RequestMapping` method is a source boundary; `binding=false`, reassignment before the call, fixed or copied entities, domain mismatches, missing or duplicate entities, and ambiguous service types are rejected. The repository receiver must be a direct official generic type or one unique project interface extending it, and the first `save` argument must be the traced value. An attribute-applicable official `@InitBinder` on the exact `WebDataBinder` receiver retains `setAllowedFields` as `explicit-binding-allowlist` and `setDeclarativeBinding(true)` as `constructor-only-binding`. `setDisallowedFields` remains reviewer evidence because Spring documents denylist fragility and recommends allowed fields. `@Valid`, authentication, endpoint authorization, setters, JPA annotations alone, or repository use do not authorize writable properties.

**Executable evidence.** The paired Spring Boot 4.1 fixtures share the same controller, service, JPA repository, entity, Hibernate, H2, route, and submitted fields. The positive binds `administrator=true` directly onto `Account` and persists it; its MockMvc witness reads the H2 row and proves the privilege bit is true. Feed each repair only the current gap inventories and stop as soon as both inventories close. Require `coverage.json` to be a single parsed object with exact inventory paths and canonical scalar dispositions; broad rewrites use a serializer, parse-and-set verification, and atomic replacement rather than repeated textual edits. In addition, require host-observed proof of a successful built-in `view` for every exact immutable inventory path before its coverage surface can close.

**Why.** A packaged production-code self-scan directly opened every one of its 88 immutable inventory paths and completed all six discovery passes, but its final bounded repair used line-oriented shell edits against JSON. The resulting document had valid-looking content followed by trailing bytes, a misspelled path, and nested object-valued dispositions. One repair turn was too brittle for an otherwise recoverable serialization defect, while accepting the backup's `status: "present"` values would have manufactured 88 security conclusions that the contract did not contain.

**Evidence.** The first session completed 61 assistant turns and 150 successful tools, with one correctly denied read outside the scanner profile. It resolved `auto` to `gpt-5-mini`, reported zero premium requests, recorded 27.110705 AIU-equivalent usage, and had no session, authentication, quota, credit-limit, or safety-classifier error. Copilot viewed all 88 exact production paths; the deterministic auditor converted malformed coverage into 88 gaps and prevented a false successful result. A second packaged run then demonstrated the inverse weakness: the final contract claimed complete coverage with 88 canonical `rejected` surfaces, but the SDK receipt proved 0 direct production-file views. That session completed 41 assistant turns and 42 successful tools with one correctly denied out-of-scope read, zero premium requests, no session error, and 15.390385 AIU-equivalent usage. Its successful exit is negative acceptance evidence: canonical model-authored rows alone did not prove review.

**Regression evidence.** Tests prove first- and later-attempt closure, use of the newest host inventory, exhaustion of all three repairs, invalid-bound rejection, transport-cause preservation, serialization guidance, and hostile-inventory containment. They also prove that only successful built-in repository views enter the host-owned review set: failed views, shell calls, MCP tools named `view`, and out-of-root paths do not. A closed canonical surface without matching host evidence becomes `missing_direct_file_review`; the same surface closes after its exact view succeeds. The complete suite passes 670 tests and 5,949 assertions.

**Liveness evidence and refinement.** Enforcing direct review on the same 88-file production scope raised observed coverage from 0/88 to 88/88, but the model replayed almost the entire inventory before successive artifact operations. The one-hour external acceptance ceiling stopped the run after 68 assistant turns, 2,681 built-in views, 2,694 successful tools, and 27.919905 AIU-equivalent; it recorded zero premium requests and no session error. Thirteen grep failures came from Copilot CLI 1.0.78-3 attempting an obsolete 1.0.77 bundled-ripgrep path. The remaining coverage draft used `path` rather than the required `label`, so the host retained 88 gaps. This is safe but not production-efficient. Correction inventories now expose `directFileReviewObserved`: a true value directs a structural coverage repair without a reread, while false still requires a successful built-in view. Scanner skills make the initial inventory pass read-once across tool calls and compaction and explicitly forbid substituting `path` for `label`.

**Scoped acceptance and mode binding.** A packaged five-file production scan reduced replay to 28 views total and proved all five exact paths, but final sealing rejected repository mode where the selected target required `scoped_path`. Per-file closure alone cannot prove target semantics, so the trusted host now supplies the exact expected mode in the runtime map and initial prompt. The closure inventory independently compares it and emits a synthetic `coverage.mode` row with exact expected and actual values; this structural row never requests repository rereads. Repeating the identical packaged scan completed in 8m53s after repair 1/3: 5/5 exact direct views, 19 total views, 35 assistant turns, 36 successful tools, one correctly denied out-of-scope read, zero premium requests, no session error, and 10.880370 AIU-equivalent. Coverage was complete `scoped_path` with zero deferred work or closure gaps. All 10 sealed artifact hashes reproduced and SARIF was nonempty. The complete suite passes 670 tests and 5,949 assertions.

**Safety boundary.** Extra turns improve recovery, not trust. The host never maps `present`, descriptive prose, missing dispositions, object values, or misspelled paths to `no_issue_found`. It never creates model evidence or coverage decisions. Direct-review evidence comes only from successful Copilot SDK tool-completion events for the built-in file viewer, normalized beneath the staged repository, and resets on each fresh session. Every repair remains finite, the exact same deterministic gates run after each attempt, and unreadable, unreviewed, or incomplete state still fails the scan.

**Consequence.** A structurally damaged draft can receive more than one chance to become auditable without replaying the expensive discovery phase or weakening acceptance. Future increases to the repair budget must remain capped and evidence-driven; they must not become an unbounded loop or a substitute for deterministic artifact validation.

## 2026-08-03 — Model OkHttp SSRF at dispatch, not request construction

**Decision.** Treat an OkHttp URL flow as executable SSRF evidence only when a typed `Request` reaches a typed `OkHttpClient.newCall(...)` and the resulting call is executed or enqueued. Support direct chaining and a prepared typed `Call`, while rejecting intervening reassignment and statement-boundary leakage.

**Why.** A request object or `newCall` value can be constructed and never sent. Matching those intermediate states inflated recall at the expense of findings that a developer could not reproduce. Dispatch is the security boundary that turns attacker-controlled URL data into an outbound request.

**Evidence.** The regression corpus includes imported and fully qualified APIs, aliases, inline construction, direct client construction, later execution, inert construction, unexecuted calls, unrelated `execute` methods, separated builders, local type shadows, and input/call reassignment. Vulnerable and safe Maven witnesses exercise OkHttp 5.3.0 against a loopback server.

**Consequence.** This bounded model intentionally misses highly dynamic dispatch that cannot be tied to the request with local typed evidence; the AI review pass remains responsible for those cases. Future extensions should add explicit data-flow evidence rather than relax the dispatch requirement.

## 2026-08-03 — Share behavior, isolate platform presentation and state

**Decision.** Move scanner orchestration and GUI state into a platform-neutral .NET 8 project. Keep WPF and the Linux presentation shell separate, and inject a small immutable platform profile for executable discovery, settings, path comparison, scan history, and benchmark output names.

**Why.** Duplicating the orchestration in two GUIs would cause security-sensitive drift in command construction, cancellation, sealed-artifact acceptance, and benchmark handling. Sharing presentation code would instead couple Linux to Windows-only assemblies. A narrow platform profile preserves one behavioral implementation without erasing native UI differences.

**Isolation.** Both applications use the scanner's `COPILOT_SECURITY_HOME` contract and `copilot-security-home` runtime directory. Linux GUI preferences and generated history use Linux-specific names, while Windows retains its established paths. Neither profile reads or writes another scanner's runtime names.

**Failure behavior.** Executable discovery accepts only actual runnable files; Linux additionally requires an execute bit. A relative `XDG_CONFIG_HOME` is invalid under the XDG convention and is ignored in favor of the user's `.config` directory, avoiding a startup crash or a working-directory-relative settings file.

## 2026-08-03 — Use a native Linux presentation with headless and X11 gates

**Decision.** Implement the Linux interface in Avalonia 12 on .NET 8, while keeping every scanner-affecting operation in the shared desktop/core projects. Publish a self-contained `linux-x64` directory and package it with conventional freedesktop metadata rather than requiring a system .NET installation.

**Why.** Avalonia provides one Linux-native control tree that can run under X11, WSLg, and a headless test platform. A self-contained directory is larger than a framework-dependent executable but produces a predictable operator experience and permits the runtime patch to be pinned, audited, and deliberately upgraded.

**Verification boundary.** The project declares `linux-x64` as its runtime identity so direct, transitive test, and self-contained publish restores all validate against the same committed lock graph. The non-graphical smoke mode validates platform/state contracts without loading graphics. The headless test loads the complete XAML tree and verifies tabs, data grids, commands, bindings, report surface, and state paths. CI then starts the published binary under `xvfb-run`, covering native Linux loading separately from headless rendering.

**Packaging boundary.** The installer refuses an incomplete payload before writing system paths. It copies only the published application and fixed launcher/desktop/icon files. Scanner state and preferences remain per-user and are never installed below `/opt` or copied from Windows.

**Standalone payload.** The release archive also carries the inspected npm scanner package plus production dependencies resolved from the committed pnpm lockfile on Linux. The GUI looks for this adjacent `scanner/bin/copilot-security.mjs` first and falls back to the source-checkout layout only for development. The scanner code is immutable application content; its mutable state still lives exclusively below the per-user scanner home.

## 2026-08-03 — Make the model protocol independent of shell expansion

**Decision.** Attach an allow-listed JSON object containing exact non-secret host runtime values to every initial, correction, and closure turn. The object is framed as immutable operational data, JSON-escapes control characters, escapes prompt-tag metacharacters, excludes unknown scanner-prefixed values and secrets, and directs the model to use decoded strings directly with built-in file tools. Shell access remains optional and must not be used merely to discover paths.

**Why.** A native Ubuntu live scan received only literal `$COPILOT_SECURITY_*` references. Copilot attempted to resolve them with `bash`, but its sandboxed shell could not start before `bubblewrap` was installed. It then tried to create artifacts in the read-only repository snapshot and the scanner correctly failed closed with no canonical drafts and four coverage gaps. Environment variables are still useful to trusted processes, but asking the model to expand them creates an unnecessary platform dependency.

**Evidence.** After exact values were added, the same deep OkHttp scan used built-in file operations to create and reopen `scan-manifest.json`, `findings.json`, `coverage.json`, and 18 discovery artifacts and receipts beneath the authorized Linux scan directory. Host reconciliation reported zero coverage gaps. The session recorded 48 successful sandboxed tool completions and no session error. Tests cover Windows and POSIX paths, hostile closing-tag text, newlines, quotes, unrelated secrets, and unknown scanner-prefixed values.

**Consequence.** Linux installations should still provide `bubblewrap` because Copilot may legitimately use its sandboxed shell for bounded analysis, but artifact correctness no longer depends on it. The prompt map must remain an explicit allow-list; never replace it with serialization of the whole process environment.

## 2026-08-03 — Validate evidence references semantically

**Decision.** Treat a data-flow endpoint or nested validation/attack-path reference as valid when it exactly names an ID in that finding's `codeEvidence` array, regardless of the ID's display length. Recursively reject every unknown value under `evidenceRefs`, while allowing prose in the separate validation `evidence` field.

**Why.** The live Linux scan produced a grounded CWE-918 finding with source `e1`, sink `e2`, exact repository snippets, validation steps, reachability, broken controls, and counterevidence. The deterministic gate nevertheless rejected `e1` and `e2` because its generic prose heuristic required strings of at least three characters and inspected only top-level references. Length is appropriate for narrative substance, not referential integrity.

**Evidence.** The preserved finding originally returned `missing_validation_evidence`, `incomplete_attack_path_dataflow`, and `missing_attack_path_evidence_refs`. The revised gate re-audits the same bytes with no gap. A dedicated regression covers short source/sink IDs in validation evidence, nested steps, and data-flow endpoints; the existing unknown-reference case continues to fail.

**Consequence.** Future quality gates must distinguish prose-quality checks from identifier-resolution checks. Evidence IDs are meaningful only through exact membership in the local finding graph; artifact paths, dangling IDs, empty arrays, and merely long strings must never receive equivalent credit.

## 2026-08-03 — Recover exact coverage aliases without guessing

**Decision.** When a model-authored coverage surface omits or corrupts `disposition`, accept `outcome` or `status` only if its value is an exact member of the canonical coverage-disposition set. Prefer `outcome` over `status`, preserve an already-valid `disposition`, and continue to force `needs_follow_up` plus partial coverage for every absent, descriptive, or otherwise ambiguous value.

**Why.** The first acceptance scan from the inspected Linux release tarball found and fully traced the intended multi-hop OkHttp SSRF, but the model wrote `status: "no_issue_found"` for `pom.xml` without the schema-required duplicate `disposition`. Treating that exact canonical value as unknowable created a false incompleteness result after successful review. Broad natural-language mapping would have hidden genuinely unresolved surfaces, so recovery remains deliberately narrow.

**Evidence.** The 4m11s native WSL run sealed hashed findings, coverage, report, discovery, and validation artifacts and exported SARIF. Its only incomplete surface had the exact canonical status and a real discovery receipt; no deferred row, missing inventory path, quota failure, refusal, or session error existed. Integration regressions reproduce that non-finding metadata shape: exact `no_issue_found` closes complete coverage, while `looks clean` remains `needs_follow_up` and partial. The corrected tarball then completed the same deep fixture in a fresh WSL directory with complete coverage, no deferred work, one high-confidence CWE-918 finding, and zero deterministic quality gaps. Recomputed hashes matched all five manifest records, and the nonempty SARIF/report outputs were present. The complete suite passes 666 tests and 5,918 assertions.

**Consequence.** This is a syntax recovery, not a security conclusion. The finalizer may normalize an exact canonical duplicate field, but it must never translate prose such as “looks clean” into a closed review or use an alias to override a valid canonical `disposition`.

**Follow-up evidence.** The successful session still recorded eight failed creates against absent artifact parents and three failed views of not-yet-created JSON files before recovering to 38 successful sandboxed tool calls. The fixed parent-directory problem is addressed by the host preparation decision below; required root drafts remain model-owned and intentionally absent until authored.

## 2026-08-03 — Prepare directories, never evidence

**Decision.** Before model execution, the trusted host creates a fixed private directory skeleton for context, six stable deep-discovery pass IDs, coverage, validation, reconciliation, attack-path, and findings artifacts. The host does not create `scan-manifest.json`, `findings.json`, `coverage.json`, `report.md`, receipts, ledgers, or finding evidence.

**Why.** Copilot's built-in file creation tool writes files but does not create missing parents. The accepted WSL session spent eight failed operations trying to write legitimate threat-model, pass-receipt, validation, and attack-path files beneath documented parents. Depending on a shell `mkdir` fallback made artifact production less portable and wasted model turns.

**Safety boundary.** Output validation supplies a fresh private canonical directory, archives a prior scan before reuse, and rejects nonempty or symlink output roots. Host preparation uses only a compile-time list beneath that directory. Empty prepared directories are not included in the sealed artifact manifest and cannot satisfy required-file, receipt, evidence, coverage, or quality gates.

**Evidence.** The runtime regression verifies all fixed directories on the real inventory-preparation path and separately proves that all four required root drafts remain absent. The focused runtime suite passes 13 tests and 65 assertions; the complete scanner suite passes 666 tests and 5,918 assertions.
