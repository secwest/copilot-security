# Design log

This log records consequential implementation decisions, their evidence, and the tradeoffs that future scanner work must preserve.

## 2026-08-03 — Bind Spring mass assignment to the persisted domain object

**Decision.** Emit a bounded Spring CWE-915 hypothesis only when an official `@ModelAttribute` parameter on an official state-changing MVC controller has the same simple domain type as the object passed to an official typed Spring Data `CrudRepository` or `JpaRepository` `save`. Require that type to resolve to exactly one official Jakarta or legacy Javax JPA entity inside the same Maven project. Preserve the same object directly, through one uniquely resolved service, or through exactly two uniquely resolved service boundaries.

**Why.** Spring MVC documents that `@ModelAttribute` uses constructor and property binding by default, explicitly warns that model binding can expose security-sensitive properties, and advises dedicated web-binding objects or allowed-field configuration. Spring Data documents `save` as persisting the supplied entity. A generic annotation-plus-method-name signal would be noisy: DTO projection, fixed entity construction, unrelated save arguments, GET handlers, local lookalikes, and mismatched repository domains are common counterexamples. Exact parameter, domain, receiver, and argument identity captures the dangerous boundary without treating ordinary form handling as a vulnerability.

**Type, flow, and control boundary.** The controller stereotype, mapping, model annotation, binder annotation and type, repository base, and entity annotation must be official imports, wildcards, or fully qualified names without a conflicting local declaration. Only POST, PUT, PATCH, or an equivalent official `RequestMapping` method is a source boundary; `binding=false`, reassignment before the call, fixed or copied entities, domain mismatches, missing or duplicate entities, and ambiguous service types are rejected. The repository receiver must be a direct official generic type or one unique project interface extending it, and the first `save` argument must be the traced value. An attribute-applicable official `@InitBinder` on the exact `WebDataBinder` receiver retains `setAllowedFields` as `explicit-binding-allowlist` and `setDeclarativeBinding(true)` as `constructor-only-binding`. `setDisallowedFields` remains reviewer evidence because Spring documents denylist fragility and recommends allowed fields. `@Valid`, authentication, endpoint authorization, setters, JPA annotations alone, or repository use do not authorize writable properties.

**Executable evidence.** The paired Spring Boot 4.1 fixtures share the same controller, service, JPA repository, entity, Hibernate, H2, route, and submitted fields. The positive binds `administrator=true` directly onto `Account` and persists it; its MockMvc witness reads the H2 row and proves the privilege bit is true. The control scopes `WebDataBinder.setAllowedFields("displayName")` to the `account` attribute; its witness proves `displayName` persists and the submitted privilege bit remains false. Focused regressions cover exact fixture provenance, same-file fully qualified types, a two-service relay, exact allowlist and constructor-only controls, wrong-attribute binders, denylist non-promotion, disabled binding, GET handlers, DTO projection, reassignment, local shadows, repository/entity mismatches, missing entity identity, ambiguous service types, and reviewer guidance.

**Acceptance evidence.** Nine focused tests pass 39 assertions, and the adjacent Java/framework gate passes 43 tests and 188 assertions across seven files. Both real Maven fixtures pass their one-test Spring MVC/Hibernate/H2 witnesses. The complete suite passes 729 tests and 6,291 assertions across 100 files with 19 intentional environment-specific skips and no failures. Deterministic review emits one exact vulnerable controller-to-service-to-`save` path with no control, the paired path with its exact allowlist control, and no production-source mass-assignment hypothesis. A fresh-key 128-commit self-scan examines 1,084 current plaintext files and 2,362 reachable historical plaintext blobs totaling 53,388,170 bytes with zero candidates, complete history, and no truncation. Formatting, generated-model drift, TypeScript checking, the production build, and the production advisory query are clean. The 203-entry archive passes isolated installation, public import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** Review receives an exact request-binding-to-persistence hypothesis rather than a generic mutable-entity warning, plus narrowly typed control leads that still require semantic validation of sensitive writable fields and protected effects. ControllerAdvice binders, Kotlin syntax, records and constructor metadata, nested property paths, collection binding, custom `WebBindingInitializer` policy, custom repository implementations, `EntityManager` operations, reactive repositories, and paths beyond two service boundaries remain future typed extensions; they should be added with paired runtime controls rather than by weakening identity requirements.

## 2026-08-03 — Require typed Spring Data object and principal provenance

**Decision.** Add a bounded Spring CWE-639/CWE-862 hypothesis only when an annotated or servlet-derived identifier reaches an official typed Spring Data `findById` lookup or an explicitly declared owner-qualified derived query, directly or through at most two uniquely resolved Java service boundaries. Retain same-query ownership only when its value comes from a real typed Spring Security `Authentication`, Java `Principal`, or official `SecurityContextHolder`. Retain `@PostAuthorize` only when official Spring pre/post method interception is active, an official Spring-managed read method compares the returned object's owner-like field with `authentication.name`, and no save, delete, or flush precedes the decision.

**Why.** Spring Data documents `findById` as the reserved identifier lookup regardless of an entity's identifier-property name, while derived query names add property predicates. Spring Security method authorization is not active merely because its starter is present: `@EnableMethodSecurity` or the legacy enabled equivalent must activate interception. Its own guidance identifies return-object post-authorization as useful for IDOR-style reads and warns against applying it after database writes. Authentication, endpoint roles, repository use, and opaque identifiers therefore do not prove authorization for the selected object.

**Type, flow, and control boundary.** A repository must be an official imported or fully qualified Spring Data interface, or one unique local interface that extends such a type inside the same Maven project. Owner-qualified derived methods must be declared on that interface. Local `JpaRepository`, `Authentication`, `Principal`, `SecurityContextHolder`, stereotype, `PostAuthorize`, and method-security shadows are rejected. The request expression must reach the first lookup argument without reassignment through every recorded controller/service parameter. An attacker-supplied owner parameter, role-only expression, inactive method security, a different return property, a policy on a non-managed class, or authorization after a write remains non-control evidence for the mandatory review turn.

**Executable evidence.** The paired Spring Boot 4.1 fixtures share a real controller, service, JPA repository, entity, Hibernate, and H2 topology. The positive keeps authenticated endpoint access and calls `findById` with the route key; its Spring test seeds two customers and proves the first can retrieve the second customer's invoice. The control declares `findByIdAndCustomerId`, binds the second predicate to the typed `Authentication.getName()` value, and proves the same foreign key is rejected while the caller's own invoice remains available. Focused tests independently cover exact fixture provenance, active versus inactive return-object policy, role-only and post-write exclusions, typed versus attacker-controlled principal expressions, fixed and reassigned IDs, untyped and local-shadow repositories, same-file and two-service paths, and reviewer guidance.

**Acceptance evidence.** Ten dedicated tests pass 37 assertions. The adjacent Java/framework and residual-risk gate passes 119 tests and 1,288 assertions across eight files with one intentional platform skip, and both real Maven fixtures pass their one-test Spring/Hibernate/H2 witnesses. The complete suite passes 720 tests and 6,252 assertions across 99 files with 19 intentional environment skips and no failures; an initial managed-sandbox run correctly exposed that the Windows ACL and child-Python contract tests require their authorized native filesystem boundary, and the authoritative native run passed them. Deterministic review emits the exact vulnerable controller-to-service-to-`findById` path with no control, the paired `findByIdAndCustomerId` path with its typed principal binding, and no production TypeScript Spring object-authorization hypothesis. A fresh-key 128-commit self-scan examines 1,066 current plaintext files and 2,350 historical plaintext blobs totaling 53,295,906 bytes with zero candidates, complete history, and no truncation. The production advisory query is clean, and the 203-entry archive passes isolated installation, public import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** Java review receives a concrete object-reference path and narrowly typed control candidates instead of a generic missing-annotation warning. Kotlin syntax, composite identifiers, specifications/criteria queries, Querydsl, custom repository implementations, relationship policies, global filters, multi-project builds, and policy handlers beyond the bounded method remain review work. Future extensions should model those concrete APIs and activation mechanisms rather than widening ubiquitous method or annotation names.

## 2026-08-03 — Separate ASP.NET endpoint access from EF resource authorization

**Decision.** Add a bounded ASP.NET Core CWE-639/CWE-862 hypothesis only when an explicitly bound or request-derived identifier reaches a typed EF Core `DbSet` or `DbContext` single-record lookup, directly or through a uniquely resolved C# service path. Retain a same-query ownership predicate only when its value is authenticated-principal-shaped. Retain imperative resource authorization only when a typed `IAuthorizationService` receives `User` and the exact returned entity, its `Succeeded` result is checked, and the denial path fails closed before the protected effect.

**Why.** CodeQL's C# missing-function-level-access-control query is deliberately medium precision and addresses action access. ASP.NET's own resource-authorization guidance states that declarative attributes run before resource loading and do not suffice for a decision about the loaded object. EF Core `Find` and `FindAsync` select an entity by primary key, including from the tracking cache, without adding an ownership predicate. Treating `[Authorize]`, a GUID, or EF use as safety would therefore preserve the central BOLA failure rather than model it.

**Type, flow, and control boundary.** A sink receiver must be a real imported or fully qualified EF `DbSet`/`DbContext` declaration, not a ubiquitous method name, untyped store, local shadow, comment, or string. The exact lookup argument must retain the controller-bound parameter through non-reassigned locals and every typed service argument. Owner-like request parameters remain attacker-controlled. A named `authenticated*Id`, `current*Id`, `principal*Id`, `actor*Id`, or session-derived value in the exact query is only a lead whose provenance the correction pass must prove. A resource-policy call on another entity, a discarded result, a success check without a fail-closed denial branch, UI visibility, or authorization after disclosure/mutation is not a control.

**Executable evidence.** The paired .NET 8 fixtures use the same controller, route, repository, EF entity, and InMemory provider topology. The positive retains `[Authorize]` and passes the route primary key to `DbSet.FindAsync`; its witness seeds two customers and proves the attacker's selected key returns the victim invoice. The control binds invoice and authenticated customer IDs in one `SingleOrDefaultAsync` predicate; its witness proves cross-customer selection returns null while the caller's own invoice remains available. Both fixture graphs compile without warnings and the official NuGet advisory query reports no vulnerable direct or transitive package. Seven focused tests pass 28 assertions across exact cross-file provenance, enforced exact-resource policy checks, query variants, reassignment, fixed IDs, untyped and shadow APIs, attacker owner filters, endpoint attributes, wrong resources, ignored results, comments, strings, and reviewer guidance.

**Acceptance evidence.** The new ASP.NET lane and adjacent framework/residual-risk gate passes 110 tests and 1,272 assertions across eight files with one intentional platform skip. The first broad run exposed a shared multiline-parameter regression in the existing ASP.NET path and SSRF models; scoping the stronger reassignment proof to the object-authorization model and parsing only the C# method body restored both lanes without accepting reassigned record IDs. The corrected complete suite passes 710 tests and 6,215 assertions across 98 files with 19 intentional environment skips and no failures. Deterministic review emits the exact vulnerable route-to-repository-to-EF path with no control, the paired path with its same-query principal binding, and no production TypeScript object-authorization hypothesis. A fresh-key 128-commit self-scan examines 1,048 current files and 2,323 historical plaintext blobs totaling 52,677,933 bytes with zero candidates, complete history, and no truncation. The production advisory query is clean, and the 203-entry archive passes isolated installation, public import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** ASP.NET review now receives object, principal, and policy provenance rather than a generic missing-attribute warning. Navigation-property ownership, global query filters, custom repositories without typed EF boundaries, minimal APIs, policy handlers across another service boundary, and role/relationship policies remain review work. Future extensions should resolve those concrete mechanisms explicitly rather than weakening receiver identity or promoting authentication-shaped text into authorization.

## 2026-08-03 — Model object authorization as identifier, object, principal, and action binding

**Decision.** Add a bounded Node/TypeScript CWE-639/CWE-862 hypothesis only when a request-controlled object reference reaches the exact argument of a recognized single-record lookup, directly or through a repository-relative wrapper. Retain an owner/tenant/account/customer/user/organization/workspace predicate only when the same lookup binds it to an authenticated-principal-shaped value; separately retain a post-lookup owner comparison or explicit policy call on the returned object before the bounded function ends.

**Why.** OWASP API1 defines broken object-level authorization around a client-supplied object identifier and missing permission for the requested operation on that object. CWE-639 likewise requires a user-controlled record key that authorization fails to constrain. Authentication, endpoint access, opaque identifiers, and an ORM API do not answer that question. Prisma's official client reference confirms that single-record `where` inputs can include additional non-unique fields specifically for permission checks, making principal-bound query filtering a concrete control without claiming it is the only valid policy design.

**False-positive boundary.** The sink argument—not the entire call line or nearby file—must directly contain the request expression, a non-reassigned local derived from it, or the exact exported wrapper parameter. Owner-like request fields remain attacker-controlled and are not principal evidence. A current-user value elsewhere in the function, a random UUID, comments, strings, fixed lookup IDs, reassigned IDs, or a check on a different record is not a candidate control. Named owner parameters crossing a second argument remain leads that the correction pass must trace back to trusted authentication state. The host emits a hypothesis, never a vulnerability verdict; disclosure/mutation reachability and permission failure still require independent proof.

**Multiline boundary.** Exported JavaScript/TypeScript function declarations and repository calls are parsed from at most 13 structural lines. This restores ordinary formatter-wrapped signatures and invocations without scanning arbitrary text or allowing string/comment braces and calls to create summaries. The same bounded parser improvement applies to every existing Node framework model.

**Evidence.** A strict four-case manifest pairs the existing same-file invoice exploit/control with new cross-file repository wrappers. Seven dedicated tests pass 36 assertions and prove exact same-file and cross-file flow, multiline generic Prisma-style lookups, principal-bound query filters, post-lookup ownership checks, and rejection of fixed, unrelated, reassigned, comment/string, attacker-owner, and unrelated-principal cases. The broader Node framework and residual-model gate passes 93 tests and 1,243 assertions with one intentional platform skip and no failures. The first complete run caught declaration-line drift when a blank line preceded an exported wrapper; requiring the current structural line to begin the declaration restored both existing command-flow paths without weakening multiline support. The corrected complete suite passes 703 tests and 6,187 assertions across 97 files with 19 intentional environment skips and no failures. A deterministic self-review emits the vulnerable cross-file fixture, its principal-bound control, and an existing post-lookup-authorized benchmark path, with no uncontrolled production-code object-authorization hypothesis. A fresh-key 128-commit self-scan examines 1,028 current files and 2,317 historical plaintext blobs totaling 52,549,127 bytes with zero candidates, complete history, and no truncation. The production advisory query is clean, and the 203-entry archive passes isolated installation, public import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** The correction pass receives an ordered object-reference path and concrete authorization leads instead of lexical lookup/authentication co-occurrence. Dynamic repository dispatch, destructured lookup aliases, policy engines outside the bounded function, and richer relationship/role policies remain review work; future extensions should preserve explicit object, principal, action, and control provenance rather than convert naming conventions into conclusions.

## 2026-08-03 — Bind Axios SSRF to module identity and the destination argument

**Decision.** Recognize Axios outbound sinks only after proving a real default, namespace, TypeScript import-equals, or CommonJS binding to the `axios` package, or a bounded non-reassigned client created from that binding. For method calls, treat only the first URL argument as destination flow; for `request(...)`, also resolve the configuration object's `url` property. Carry instance configuration into candidate controls without treating the request body or unrelated call text as URL evidence.

**Why.** Axios clients are commonly hidden behind `axios.create(...)`, so literal `axios.get(...)` matching misses production flows. Widening `.get`, `.post`, or `.request` as generic sinks would instead misclassify local objects and request bodies. Axios also prepends `baseURL` only to relative URLs by default: an attacker-supplied absolute URL can override that server-owned base. `allowAbsoluteUrls: false` closes the authority override, but does not by itself make attacker-controlled relative paths safe because traversal and endpoint-selection remain separate boundaries.

**False-positive boundary.** Module bindings and client creation are read from comment-aware structural code, client reassignment invalidates the identity, and block- or line-comment imports and controls are ignored. `post`, `put`, and `patch` bodies are never inferred as destinations. Fixed destination selection, exact-host parsing, relative-path validation, disabled absolute override, disabled redirects, and address pinning remain independent candidate controls that the correction pass must prove against the same runtime value and sink.

**Evidence.** The paired benchmark preserves an exact request-query-to-wrapper-parameter-to-`client.get` path for the exploitable instance and retains exact-key selection, `allowAbsoluteUrls: false`, and `maxRedirects: 0` on the safe control. Six dedicated regressions pass 31 assertions across vulnerable and safe fixtures, default and namespace ESM, TypeScript import-equals, CommonJS, multiline generic calls, and request-config URLs; they reject local and parameter shadows, body-only flow, reassigned roots and instances, unrelated configuration, and comment/string-only controls. The broader SSRF and residual-model gate passes 82 tests and 1,156 assertions with one intentional platform skip and no failures. The complete rebuilt suite passes 696 tests and 6,144 assertions across 96 files with 19 intentional environment skips and no failures. A deterministic self-review emits only the two new Axios benchmark rows, with the expected three controls on the negative and none on the exploit; no production-code Axios hypothesis is present. A fresh-key self-scan examines 1,018 current plaintext files and 2,302 reachable historical blobs totaling 52,004,864 bytes, finds zero candidates, and completes without truncation. The production advisory query is clean, and the 203-entry archive passes isolated installation, public import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** Axios coverage gains real instance and wrapper reach without turning ubiquitous method names into noisy sinks. Dynamic factories, destructured methods, computed configuration, and aliases beyond the bounded local model remain review work; future support should add explicit binding and argument evidence rather than weakening identity or destination-role checks.

## 2026-08-03 — Scan reachable Git objects without turning history into a plaintext channel

**Decision.** Extend the trusted pre-model secret pass from current files to unique plaintext blobs reachable from a bounded newest-commit horizon across refs. Default to 128 commits, accept an explicit `0..2048`, and deduplicate the same repository-scoped HMAC rule/path/value identity across revisions. Preserve at most eight opaque blob IDs plus the complete bounded object count; never persist or prompt the value.

**Why.** Removing a credential from the working tree does not remove it from clones, branches, caches, or reachable repository objects. Gitleaks scans Git patches, GitHub describes whole-history branch scanning, and TruffleHog treats Git version history and fingerprint deduplication as first-class secret context. A current-tree-only negative is therefore a material false-negative class. Patch parsing, however, couples correctness to attacker-controlled diff syntax, rename quoting, hunk state, and text-conversion configuration. Reading typed Git objects gives exact immutable content and paths without checking out a historical tree or interpreting patch grammar.

**Trust and privacy boundary.** Git is resolved outside the protected repository through the existing trusted-executable policy. History commands use argument arrays without a shell; delete ambient `GIT_*` variables; disable system/global configuration, replacement objects, lazy fetching, optional locks, and pagers; suppress command diagnostics; and never contact an issuer or remote. Because disabling global configuration also removes user-level safe-directory declarations, the scanner supplies only its already-canonical target root as an exact command-line `safe.directory`; it does not restore ambient trust. Object IDs and paths are parsed as bounded untrusted data. Type and size are batch-checked before content is batch-read. Historical rows contain only source kind, rule, path/line, structural redaction, local keyed fingerprint, and bounded blob IDs. The correction prompt forbids `git show`, `cat-file`, patch logs, or source views merely to recover candidate bytes and forbids claiming issuer validity without separate safe evidence.

**Completion and availability boundary.** Separate caps cover a 2048-commit maximum, 8 MiB object enumeration, 8,000 named objects, 4,000 blobs, 512 KiB per blob, 64 MiB aggregate content, 8,000 candidate occurrences, eight retained object IDs per identity, and 60 seconds per Git command. `disabled`, `not_git_repository`, `unavailable`, `complete`, `partial`, and `error` remain distinct. A requested pass that lacks trusted Git, times out, encounters malformed/missing objects, or reaches a cap sets history and overall truncation; it cannot support a clean history-wide conclusion. A non-Git directory is not mislabeled as truncated because no repository history exists.

**False-positive boundary.** Generic assignment scanning rejects a quoted value only when it is a multi-segment uppercase identifier ending in a credential-specific environment suffix such as `_TOKEN`, `_SECRET`, `_KEY`, `_PASSWORD`, or `_CREDENTIAL`. It does not exclude tests, fixtures, history, all uppercase strings, or provider-specific patterns. This narrow semantic control was selected after the redacted self-scan metadata showed three historical generic candidates with exactly that identifier shape; no candidate bytes were printed or persisted during triage.

**Evidence.** A real temporary repository commits fragment-materialized GitHub, GitLab, and generic refresh credentials, creates two distinct blobs containing the same GitLab credential, deletes every candidate from the working tree, and retains placeholder/public-key controls only in history. The history benchmark returns exactly the three positive identities at 1.0 precision and recall, aggregates the duplicate blob provenance, and contains none of the materialized values in inventory or private report. Additional regressions prove a one-commit horizon excludes the older deleted objects, exact immutable path scoping excludes an adjacent historical credential, disabled and non-Git states remain complete, missing trusted Git fails incomplete, invalid depth is rejected before execution, and uppercase environment references are not mistaken for values. The production self-scan initially exposed Git's dubious-ownership failure after ambient configuration isolation; exact canonical `safe.directory` binding restored the pass without trusting global state. A fresh-key 128-commit scan then examined 1,008 current files and 2,274 historical plaintext blobs totaling 51,094,954 bytes with zero candidates, complete history, and no truncation. The complete suite passes 690 tests and 6,113 assertions across 95 files with 19 intentional skips and no failures; the production audit and 203-entry installed-package contract are clean.

**Consequence.** Deleted credentials are now deterministic high-priority leads rather than depending on a model deciding to inspect history. Future issuer validation, custom rules, encoded-secret decoding, reflog/unreachable-object scanning, or remote-source integrations must remain separately authorized and preserve local redaction, finite execution, no implicit network, explicit completion, and benchmarked negative controls.

## 2026-08-03 — Keep deterministic secret identity local, keyed, redacted, and expiring

**Decision.** Run a bounded deterministic secret pass in the trusted host before any model turn. Match high-confidence provider formats first, then credential-name assignments only when their value has sufficient Shannon entropy. Persist and prompt only the rule, exact relative location, redacted structural shape, and an HMAC-SHA-256 fingerprint bound to the private local key, canonical repository root, rule, path, and value. Suppress a candidate only through an exact local baseline row with the same fingerprint/rule/path, a substantive justification, and a future canonical UTC expiry.

**Why.** Model-only secret discovery is nondeterministic and risks copying sensitive values into prompts, transcripts, findings, and logs. Unkeyed hashes permit offline guessing of low-entropy credentials, portable fingerprints can suppress the same secret in an unrelated checkout, line-bound identities churn on harmless edits, and permanent or reason-free allowlists become an invisible false-negative mechanism. The local keyed design gives reviewers stable identity across line movement without making fingerprints useful outside this scanner home or repository.

**Trust boundary.** The random 32-byte key and per-repository default baseline live only under `COPILOT_SECURITY_HOME/copilot-security-home/secret-scanner`. Existing links, non-regular or wrong-length keys, state that resolves outside the private home, malformed or oversized baselines, traversal paths, duplicate entries, and missing explicitly selected files fail before Copilot starts. Unix permissions are forced to `0700`/`0600`; Windows inherits the scanner's private runtime-home ACL. Reports contain active and suppressed redacted rows, while prompts omit suppressed rows and the host baseline path. The detector instructs Copilot not to reopen a candidate line merely to recover or validate its bytes. This does not claim that Copilot can never encounter source text during its independent repository review; it prevents this deterministic channel from transmitting or persisting the value.

**Scope and false-positive boundary.** Full repository scans examine bounded plaintext while ignoring links, binary data, generated dependency/build trees, and oversized input. Path and diff scans consume only the immutable host inventory. Exact provider rules take precedence over generic assignment matches on the same range. Placeholder vocabulary and low entropy are explicit countercontrols; an active row remains a candidate requiring repository and shipping context, not an automatic finding. Expired baselines reactivate without user action and remain visible in local audit counts.

**Evidence.** The fragment-materialized corpus produces 14/14 expected typed and entropy detections with zero false positives across four controls, for 1.0 recall and 1.0 precision, while asserting that no generated value appears in model inventory. Focused regressions additionally prove raw-byte absence from local reports, stable fingerprints across line moves, repository/key scoping, exact-match suppression, automatic expiry reactivation, immutable scope filtering, exact line/column location, placeholder/binary/generated-tree rejection, malformed, excessive, and linked baseline failure, traversal rejection, invalid key failure, state-link rejection, justification non-copying, candidate-byte rejection in justifications, explicit truncation status, and prompt-tag framing. POSIX CI confirmed that a linked state directory is rejected at the earlier `lstat` type gate before canonical containment; the regression therefore asserts the rejection invariant without coupling itself to the later diagnostic. CLI and SDK type checks pass, and both desktop command surfaces preserve the selected baseline as one literal shell-free argument. A no-baseline self-scan examines 1,005 bounded plaintext files and returns zero candidates without truncation after rejecting synthetic fixtures and source expressions semantically. The complete scanner suite passes 686 tests and 6,063 assertions across 93 files, with 19 platform-specific skips and no failure. Windows and Linux builds and desktop tests pass without warnings; the production advisory query is clean; and the 203-entry archive passes isolated installation, public import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** Secret detection is now a deterministic host capability instead of a prompt suggestion, with auditable exceptions that decay. Future custom rules, Git-history scanning, baseline-management UX, or additional providers must preserve the no-plaintext report/prompt contract, local keyed scope, fail-closed state validation, exact expiry semantics, and positive/negative corpus gates.

## 2026-08-03 — Preserve RazorLight key, content, and model roles

**Decision.** Extend the typed ASP.NET CWE-1336 model to `IRazorLightEngine.CompileRenderStringAsync` only when the receiver is proven through an imported or fully qualified RazorLight engine type or a completed engine-builder chain. Treat the second `content` argument as runtime template source, preserve named-argument semantics when arguments are reordered, and keep the first template key and third model argument out of the source flow.

**Why.** RazorLight compiles C# Razor source at runtime, but adjacent APIs have different trust boundaries. The official interface defines `CompileRenderStringAsync<T>(key, content, model, viewBag)` as direct string compilation and rendering, while `CompileRenderAsync<T>(key, model, viewBag)` resolves a project template by key. Broad method-name or argument-co-occurrence matching would report safe model binding and template selection; a string-source-only model closes a high-impact gap without paying that false-positive cost.

**Type and argument boundary.** Unqualified calls require `using RazorLight;`, a real `IRazorLightEngine` or `RazorLightEngine` receiver, and no local engine-type shadow. Fully qualified declarations reject a locally defined `RazorLight` namespace lookalike. `var` receivers are accepted only after a `RazorLightEngineBuilder` chain reaches `Build()`. A named `content:` argument wins regardless of textual order. Flow into `key:`, `model:`, or `viewBag:`, fixed content, incomplete builders, and reassigned request values is counterevidence.

**Evidence.** Four focused RazorLight regressions plus the four existing Scriban regressions pass with 48 assertions. They prove exact cross-file flow, imported and fully qualified types, generic calls, completed builders, bounded aliases, reordered named content, pinned dependency floors, and CI audit retention; negatives cover model-only and key-only flow, project-template resolution, fixed content, reassignment, untyped receivers, imported and qualified shadows, incomplete builders, and text-only lookalikes. Both Web SDK fixtures compile without warnings on .NET 8. The vulnerable witness compiles `@Model.ApiKey` and discloses the server-owned model secret; the matched fixed-source witness preserves the same text as ordinary model data and does not disclose the secret. The first official NuGet audit exposed RazorLight 2.3.1's vulnerable `Microsoft.Extensions.Caching.Memory 6.0.0` and `System.Text.Json 6.0.0` transitives; the fixtures and witnesses now pin Microsoft's patched 8.0.1 and 8.0.5 floors and pass the advisory query. CI parses the JSON package graph and fails on any direct or transitive vulnerability rather than trusting the command's zero exit status; the exact Linux predicate rejects a synthetic vulnerable transitive and accepts the real clean graph. The complete scanner suite passes 678 tests and 5,997 assertions across 91 files, with 19 environment-specific skips and no failures. The 199-entry archive passes isolated installation, public-import, CLI, and all 79 bundled-plugin file checks.

**Consequence.** ASP.NET template discovery now covers two engines with distinct execution boundaries instead of flattening them into a generic render call. Future engine additions must prove the concrete receiver and source argument, preserve key/model/context roles, and ship with an executable same-topology control.

## 2026-08-03 — Model ASP.NET template injection at the parsed source argument

**Decision.** Add a typed ASP.NET-to-Scriban CWE-1336 model at the first argument of the real `Scriban.Template.Parse` API only when the parsed template reaches `Render` or `RenderAsync`. Preserve the controller source, uniquely resolved service receiver, call argument, wrapper parameter, bounded aliases, exact parse argument, and evaluation dispatch. Require a real Scriban import or fully qualified type, reject local `Template` shadows, and reject inert or reassigned parsed templates.

**Why.** Template engines expose a critical semantic distinction: attacker-controlled template grammar is executable input, while attacker-controlled values passed to a fixed template are data. API-name matching or treating every render-model value as template source would inflate false positives. Conversely, generic lexical discovery can miss a request value after it crosses an injected ASP.NET service boundary. CodeQL's high-precision Java template query makes the same source-versus-fixed-template distinction, but the documented C# query set does not provide this Scriban boundary.

**Argument and execution boundary.** Only `Template.Parse`'s first argument is template source, and parsing without rendering is inert. Its optional source-file-name metadata and parser options do not become template grammar. A fixed server-owned template parsed once remains strong counterevidence when request data is supplied only to `Render`, even if sensitive server values share the same render model. `TemplateContext`, `ScriptObject`, syntax validation, or output encoding is not automatically a sandbox for attacker-controlled source; an actual restricted context must be proven against the demonstrated capability.

**Evidence.** Four focused regressions with 20 assertions prove exact cross-file flow, imported and fully qualified Scriban types, one bounded alias, and rejection of inert same-file and cross-file parsing, parsed-template reassignment, render-only data, source-name metadata, source reassignment, shadows, absent imports, and text-only lookalikes. Both Web SDK fixtures compile on .NET 8 with Scriban 7.2.5. ## 2026-08-03 — Model OkHttp SSRF at dispatch, not request construction

**Decision.** Treat an OkHttp URL flow as executable SSRF evidence only when a typed `Request` reaches a typed `OkHttpClient.newCall(...)` and the resulting call is executed or enqueued. Support direct chaining and a prepared typed `Call`, while rejecting intervening reassignment and statement-boundary leakage.

**Why.** A request object or `newCall` value can be constructed and never sent. Matching those intermediate states inflated recall at the expense of findings that a developer could not reproduce. Dispatch is the security boundary that turns attacker-controlled URL data into an outbound request.

**Evidence.** The regression corpus includes imported and fully qualified APIs, aliases, inline construction, direct client construction, later execution, inert construction, unexecuted calls, unrelated `execute` methods, separated builders, local type shadows, and input/call reassignment. Vulnerable and safe Maven witnesses exercise OkHttp 5.3.0 against a loopback server.

**Consequence.** This bounded model intentionally misses highly dynamic dispatch that cannot be tied to the request with local typed evidence; the AI review pass remains responsible for those cases. Future extensions should add explicit data-flow evidence rather than relax the dispatch requirement.
